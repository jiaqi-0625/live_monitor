# 存储与容量规划

更新日期：2026-08-10

## 1. 规划基线

- 优化师规模：约 80 人。
- 已管理直播间：约 1000 个。
- 直播间不会全部同时开播。
- 系统容量目标：预留 300～500 路同时直播。
- 单场典型时长：约 2 小时。
- 当前轻量服务器继续用于开发和试点，不作为最终生产存储架构。

容量规划以“同时直播间数量”为主要依据，用户人数和已登记直播间总数作为账号、语料和历史数据规模依据。

## 2. 已确认的产品需求

### 2.1 优化师本机存储

- 完整转写应支持保存到优化师本机。
- 直播进行期间，服务器仍需保存实时工作数据，保证实时诊断和整场复盘正常运行。
- 直播结束并完成复盘后，本机保存完整转写，服务器按照保留期清理原始转写。
- 本机归档需要提供 TXT/JSON 等可迁移格式，不能只依赖浏览器缓存。
- 本机副本用于长期归档，不作为系统唯一副本；浏览器数据清理或电脑更换不能导致关键复盘数据不可恢复。

### 2.2 语料库文件上传

- 语料库增加文件上传入口。
- 计划支持 PDF、Word、Excel、TXT、Markdown、CSV 和 JSON。
- 原始文件保存到对象存储或优化师本机。
- 服务器只保留 AI 检索和引用所需的解析文本、分段内容及文件元数据。
- 所有语料必须使用稳定的用户 ID 隔离，不能长期只依赖优化师姓名。

## 3. 数据保留策略

| 数据类型 | 建议服务器保留期 | 长期保存位置 |
| --- | --- | --- |
| WAV 原始音频 | 复盘完成后立即压缩并删除 | 不长期保存 |
| Opus/AAC 压缩音频 | 7 天 | 对象存储或按需归档 |
| 完整转写 | 30 天 | 优化师本机归档 |
| 原始大屏接口数据 | 7 天 | 原则上不长期保存 |
| 标准化指标 | 1 年 | PostgreSQL |
| AI 实时诊断 | 长期 | PostgreSQL |
| 整场直播复盘 | 长期 | PostgreSQL |
| 语料原始文件 | 按账号配额管理 | 对象存储或优化师本机 |
| AI 使用的语料文本 | 使用期间持续保存 | PostgreSQL |

具体保留期应做成系统配置，并允许管理员按业务要求调整。

## 4. 单场及总体容量估算

每场 2 小时直播的估算：

- 转写文本：约 0.2～1 MB。
- 原始及标准化指标：约 3～10 MB。
- AI 诊断和复盘：通常小于 1 MB。
- 16 kHz 单声道 PCM WAV：约 220～250 MB。
- Opus/AAC 压缩音频：约 25～45 MB。

若 1000 个直播间每天各直播一场：

- 压缩音频约 25～45 GB/天。
- WAV 音频约 230 GB/天，因此禁止长期保留 WAV。
- 结构化数据约 4～10 GB/天。
- 压缩音频保留 30 天约需要 0.8～1.4 TB。
- 数据库 30 天数据加索引、空间预留和备份，按 500 GB～1 TB 准备。

## 5. 正式生产架构

### 5.1 数据层

- PostgreSQL：用户、直播场次、转写、标准化指标、AI 诊断、复盘、语料元数据和解析文本。
- 对象存储（OSS/COS/S3）：压缩音频及 PDF、Word、Excel 等原始语料文件。
- Redis：实时连接状态、短期缓存、任务状态和跨节点消息。
- SQLite：仅保留给本地开发和小规模试点，正式扩容前必须迁移。

### 5.2 300～500 路并发的初始建议

| 组件 | 300 路容量 | 500 路容量 |
| --- | --- | --- |
| API/WebSocket 节点 | 3 台，每台 8 核 16 GB | 5 台，每台 8 核 16 GB |
| PostgreSQL | 8 核 32 GB、500 GB NVMe | 16 核 64 GB、1 TB NVMe |
| Redis | 主从 4 核 8 GB | 主从或集群 8 核 16 GB |
| 对象存储 | 初始 2 TB、自动扩容 | 初始 3～5 TB、自动扩容 |
| 公网带宽 | 300～500 Mbps | 建议 1 Gbps |

最终节点数量必须通过 100、300、500 路分阶段压力测试确定。

## 6. 关键容量风险

- 阿里云实时语音识别需要提前确认或购买 500 路并发额度。
- 500 路每 60 秒调用一次大模型会产生约 500 次/分钟请求；应由规则引擎持续判断，仅在异常、显著变化或固定低频周期调用大模型。
- 服务端 FFmpeg 直接抓取 300～500 路直播会消耗大量 CPU；规模化使用应以浏览器扩展采集为主，服务端直接抓流作为受限备用能力。
- 多节点部署后，WebSocket 状态不能只保存在单个进程内，需要 Redis 发布订阅或专用实时消息层。
- 正式环境需要稳定用户 ID、权限控制、数据配额、审计日志和 HTTPS。

## 7. 备份要求

- PostgreSQL 每日全量备份，并保留连续 WAL，支持 7～30 天时间点恢复。
- 对象存储启用版本控制和生命周期规则。
- 备份不能与生产数据只放在同一台服务器或同一块磁盘。
- 定期执行恢复演练，不能只检查备份文件是否存在。

## 8. 实施顺序

1. 增加语料文件上传和本机转写导出。
2. 增加音频压缩、保留期和自动清理任务。
3. 建立稳定的优化师账号和用户 ID 数据隔离。
4. 从 SQLite 迁移到 PostgreSQL。
5. 将音频和原始语料文件迁移到对象存储。
6. 拆分实时网关、任务队列、媒体处理和 AI 分析服务。
7. 完成 100、300、500 路压力测试和容量复核。

## 9. 当前阶段约束

- 在 PostgreSQL、对象存储和保留策略完成前，不应直接开放到 300～500 路生产并发。
- 当前功能修改必须保持多直播间、实时转写、指标监控、AI 建议、手动结束复盘和个性化语料库的既有行为不变。
- 每个阶段完成后先执行自动化回归和线上健康检查，再进入下一阶段。
